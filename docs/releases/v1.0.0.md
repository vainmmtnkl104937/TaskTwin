# v1.0.0 — Production Release Notes

This is the first TaskTwin V1 production release. It is the result of
session 41 — the release-gating pass that follows the
`v1.0.0-rc.1` UAT stabilization session. Promotion was performed only
after the `v1.0.0-rc.1` known-issues register and the V1 release-blockers
table were both empty and the operator-gated verification matrix in the
session plan was satisfied.

## What ships

TaskTwin v1.0.0 carries the full V1 feature set delivered through
session 39, the session-40 UAT stabilization pass, and the session-41
release gate:

- Chrome extension recording with privacy-bounded event capture, semantic
  locator bundles, deterministic recording-to-Draft conversion and
  immutable recording artifacts.
- Authenticated Draft workflow editor with variables, value sources, secret
  references, ephemeral Extract outputs, deterministic Verify steps,
  Approval gates, conservative retry and attended repair, and
  privacy-filtered locator repair proposals.
- Local Runner pairing, heartbeat, separate credential, Windows Service
  mode with DPAPI-NG native unlock, signed Windows x64 releases with
  explicit protocol, schema and local-state compatibility, local update and
  rollback controller, trusted release catalog and controlled staged fleet
  rollouts.
- Control Plane: short-lived access-token authentication, immutable
  workflow versions, Workspace execution policy with deny precedence,
  deterministic scheduler with DST-safe IANA timezone occurrences,
  encrypted run inputs, append-only hash-chained audit trail, in-app
  operational alerts, and privacy-safe operational telemetry.
- Production Control Plane Docker Compose baseline with separate Web, API,
  Scheduler, Notification Worker, migration job and PostgreSQL services,
  read-only root filesystems, dropped Linux capabilities, exact-origin
  browser CORS, compressed versioned PostgreSQL backups with SHA-256
  sidecars, bounded retention, clean-database restore, restored
  audit-chain verification and a repeatable two-database DR drill.

The full feature set, invariant surface and limitations are recorded in
`docs/ai/CURRENT_STATE.md`, `docs/ai/MODULE_MAP.md` and
`docs/ai/INVARIANTS.md`.

## What this session deliberately does not change

- No new product feature, dependency or public API.
- No change to authentication, authorization, RBAC, Runner revocation or
  run-lease behaviour.
- No change to audit, alerts, telemetry, secret storage, release signing
  or fleet rollout semantics.
- No change to the Production Control Plane Docker Compose topology
  beyond pre-existing baselines.
- No change to the Local Runner SemVer, the workspace package SemVer,
  the Golden Path E2E harness, the DR drill harness or the V1 UAT
  checklist. The Runner `0.1.0` build target, run protocol, workflow
  schema, local-state schema, vault schema and platform/architecture
  declared in `packages/runner-release` are unchanged from `v1.0.0-rc.1`.
- No edit to any old Prisma migration, no schema rewrite, no automatic
  rollback, no remote Runner install, no remote Runner rollback, no
  remote shell.

## Operators

- Testers and release managers: run `docs/uat/v1-smoke-test.md` against
  a fresh Compose stack. Record pass/fail per scenario in
  `docs/uat/v1-primary.md`. File any failure into
  `docs/uat/known-issues-v1.0.0.md` with a severity from
  `docs/severity.md`.
- Production deployers: follow the deployment sequence in
  `docs/control-plane-production-deployment.md` and the operator
  procedure in `deploy/control-plane/README.md`. A pre-deployment
  `predeploy` backup is mandatory.
- DR: follow `docs/disaster-recovery.md`. Run `pnpm dr:drill` at least
  quarterly and after material persistence or recovery changes. The
  portable baseline intentionally does not provide continuous WAL
  archiving, point-in-time recovery, replication, HA, cloud backup
  service, automatic failover or automatic off-host copy.
- Runner release management: `docs/runner-update.md` and
  `docs/windows-runner-deployment.md`. The Runner update controller is
  Session 32 and is the only supported path. The trusted public-key
  registry is intentionally empty until deployment provisions a reviewed
  public key; without it, `apply` fails closed with
  `update_current_release_unverified`. Pre-Session-32 installations
  must be brought into the managed layout through a separately reviewed
  out-of-band bootstrap procedure.
- Release acquisition: `docs/runner-acquisition` and
  `packages/runner-acquisition`. Static allowlisted HTTPS source only.
  Partial downloads remain inert and are never supplied to update.

## Known limitations carried forward

See `docs/uat/known-issues-v1.0.0.md` for the live register. Limitations
inherited from earlier sessions remain unchanged; v1.0.0 does not resolve
them and they are not V1 release blockers. The V1 release blockers table
is empty at the time of promotion; any future P0 or acceptance-critical
P1 entry must block the next product release tag.
