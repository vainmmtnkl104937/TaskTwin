# Runner upgrade preflight and manual upgrade

Always verify the target release before stopping the current Runner:

```text
runner release verify <manifest> <signature> <artifact>
runner upgrade preflight <manifest> <signature> <artifact>
```

Run preflight through the currently installed trusted Runner package. Its own
embedded build identity supplies `currentVersion`; a mutable config file and
the not-yet-installed target package are not valid substitutes.

The preflight command defaults to the current user's data root. For a service
installed with another configured data root, pass that same root locally:

```text
runner upgrade preflight <manifest> <signature> <artifact> --data-root <runner-data-root>
```

The option is a local read boundary and is never reported to the Control Plane.
Using the wrong data root does not establish compatibility for the installed
service.

Verification authenticates the canonical manifest through a compiled trusted
public key, then verifies the selected Windows x64 artifact's exact filename,
size and SHA-256. Unknown keys or any mismatch fail closed.

Preflight compares the installed build version, signed target compatibility,
Windows/x64 target, current aggregate local-state schema and current Local
Secret Vault schema/protection profile. It performs bounded reads only and does
not create a marker, change a timestamp, acquire a write path, rewrite the
vault, migrate data or alter service configuration.

For schema 1, the local inspector recognizes the bounded headers of
`.tasktwin/runner-credential.json`, `runner-encryption-key.json`, and the Local
Secret Vault when present. The versioned Windows service configuration remains
independently validated by the existing service manager and is regenerated by
the explicit uninstall/install transition; preflight neither edits nor silently
migrates it.

Decisions:

- `compatible`: the target reads and preserves current persisted formats.
- `migration_required`: the target can read current data but declares a newer
  writable schema. Session 31 does not perform that migration.
- `unsupported`: an upgrade target cannot read current data or lacks the target
  artifact.
- `downgrade_blocked`: a lower target cannot read current data/profile or would
  write an older persisted schema.

## Manual upgrade

1. Keep the existing service running while verifying and preflighting files.
2. Require `compatible`; stop on every other decision.
3. Extract the verified ZIP into a new, previously absent versioned directory.
4. Confirm the extracted package reports the expected immutable version.
5. Stop and uninstall the old service explicitly.
6. Run the new package's local service-install command against the existing
   data root: `runner service install --data-root <runner-data-root>`.
7. Start it with the same `--data-root` option when non-default, then confirm
   local status and Control Plane compatibility.
8. Retain local `.tasktwin` state outside release directories.

There is no automatic download, install, migration, rollback or state
downgrade. Rolling back is another manual target verification/preflight and may
be blocked after a newer schema or vault protection profile has been written.
Pre-Session-31 or otherwise unsigned packages have no trusted compatibility
declaration and are not accepted as safe rollback targets by this flow.
